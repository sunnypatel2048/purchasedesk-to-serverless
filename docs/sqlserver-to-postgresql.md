# SQL Server to PostgreSQL: type and behaviour map for PurchaseDesk

This maps the legacy schema (`legacy/database/01-schema.sql`, SQL Server 2019, collation
`SQL_Latin1_General_CP1_CI_AS`) to Aurora PostgreSQL, column by column, and lists every behaviour that changes
between the two engines. Where the legacy behaviour is visible to clients, the evidence is a golden file
([ADR-0009](adr/0009-golden-files-define-equivalent.md)). The target schema is created by the project's own
migrations before AWS DMS copies the data (Phase 5); these are the recommendations it starts from.

## Conventions

| Topic | Recommendation | Why |
|---|---|---|
| Names | `snake_case`, unquoted (`purchase_orders.order_date`); DMS table and column rename rules map the legacy names | Quoted mixed-case identifiers make every query awkward in PostgreSQL |
| Keys | `GENERATED BY DEFAULT AS IDENTITY`, not `ALWAYS` | DMS must insert the legacy id values; `ALWAYS` would reject them |
| Times | `timestamp(3) without time zone`, holding UTC by convention | The legacy values carry no zone; DMS maps `datetime` to `timestamp`; `timestamptz` would make every writer agree on a session zone. Revisit if the new API ever needs offsets |
| Money | `numeric(19,4)` | Exact, and the same scale `money` stores (four decimals) |
| Text | `varchar(n)` with the same `n` | PostgreSQL text is Unicode, so `nvarchar` needs no special type; lengths count characters in both |

## Behaviour map

| # | Behaviour | SQL Server (legacy) | PostgreSQL / new stack by default | What the new system does | Evidence |
|---|---|---|---|---|---|
| 1 | Rounding a line amount | `ROUND(x, 2)` on decimals rounds half away from zero: 2.345 to 2.35 | PostgreSQL `round(numeric)` also goes away from zero, but C# `Math.Round` defaults to half-to-even: 2.34 | Domain code uses `MidpointRounding.AwayFromZero`; tests cover the planted half-cent lines | [order-14](../golden/api/order-14-half-cent-line.json), [write-01](../golden/api/write-01-create.json) |
| 2 | Text comparison and sort | Case-insensitive, accent-sensitive: `Northwind Traders` = `northwind traders`; `Ångström` sorts first | Case-sensitive, and byte or ICU order depending on the column collation | Supplier list ordered by `lower(name)` with an ICU collation, then `id`; parity compares the order exactly | [suppliers-list](../golden/api/suppliers-list.json) |
| 3 | Text search | `LIKE` is case-insensitive; `%`, `_` and `[...]` are wildcards, unescaped | `LIKE` is case-sensitive; no `[...]` classes | `ILIKE` with the same unescaped `%` and `_`; `[...]` in a search is treated literally (documented difference) | [search-text-urgent](../golden/api/search-text-urgent-case-insensitive.json) |
| 4 | NULLs in `ORDER BY` | First ascending, last descending | Last ascending, first descending | `NULLS FIRST` / `NULLS LAST` written explicitly on `required_by` | [search-requiredby-asc](../golden/api/search-requiredby-asc-nulls-first.json), [-desc](../golden/api/search-requiredby-desc.json) |
| 5 | Time precision | `datetime` stores 1/300 s: `.997`, `.003` | `timestamp(3)` stores milliseconds exactly | Copied values are identical; new writes have whole-millisecond values (not visible to clients beyond format) | [order-125](../golden/api/order-125-datetime-997ms.json), [order-250](../golden/api/order-250-datetime-003ms.json) |
| 6 | Date-only values in JSON | `RequiredBy` comes out as `"2026-01-21T00:00:00"` (Newtonsoft, `DateTime`) | `DateOnly` would serialise as `"2026-01-21"` | New API writes the legacy shape (decision for Phase 6: match, or change deliberately) | [order-14](../golden/api/order-14-half-cent-line.json) |
| 7 | Money in JSON | Four decimals: `13059.8900` | Depends on how `numeric` reaches the serializer | Keep the scale (`numeric(19,4)` read as `decimal`); parity checks the text | [order-14](../golden/api/order-14-half-cent-line.json) |
| 8 | JSON property names | PascalCase, nulls included | ASP.NET Core minimal APIs default to camelCase | Serializer configured for PascalCase and nulls included | all API golden files |
| 9 | Status and sort arguments | `status=pending`, `dir=asc` accepted (case-insensitive collation) | Case-sensitive comparisons would return nothing or reject | Arguments compared case-insensitively in C# | [search-requiredby-asc](../golden/api/search-requiredby-asc-nulls-first.json) (`dir=asc`) |
| 10 | Identity values after the copy | `IDENTITY` continues from the highest id | DMS copies the values but does not advance the sequences: the first insert collides | `make cutover` advances every sequence past the highest copied value | Phase 8 |
| 11 | Concurrency token | `rowversion`, 8 bytes, changes on every update; API `Version` is its base64 | No equivalent; `xmin` is not stable enough to expose | `version` column incremented by each write in the same `UPDATE ... WHERE version = @v`; API `Version` stays an opaque string | [write-03](../golden/api/write-03-approve-again-stale-version.json) |
| 12 | "Now" | `GETDATE()`: the server's local clock (UTC on EC2 and in containers) | `now()` returns `timestamptz` | Always UTC, written explicitly | write golden files (normalised `<now>`) |
| 13 | Order number | Placeholder row, then `PO-` + id in the same transaction | No placeholder needed | `nextval` first, then one insert with the final number; same format | [write-01](../golden/api/write-01-create.json), [write-14/15](../golden/api/write-15-double-submit-second.json) |
| 14 | Error contract | `THROW 50001..50005` mapped to 400, 404, 409, 409, 422 with the procedure's message | No `THROW` numbers | Domain exceptions mapped to the same statuses and the same message text | write-03, -04, -06, -08, -09 |
| 15 | Over-long line Sku | 500 "An error has occurred." (2629 on CU32, a deadlock on RTM) | Npgsql raises 22001 | **400**, a documented difference | [write-12](../golden/api/write-12-create-sku-41-chars.json) |
| 16 | Over-long scalar parameters | Not yet observed. The legacy code sizes its parameters (`@Notes NVarChar(500)`), and ADO.NET may truncate a longer value instead of failing | Npgsql sends the full value; PostgreSQL rejects it (22001) | Record the legacy behaviour in Phase 6, then decide (match, or 400); not yet covered by a golden file | not recorded |
| 17 | Double submit | Creates two orders | Same, unless prevented | Idempotency key on order creation (DynamoDB); a deliberate change | [write-14](../golden/api/write-14-double-submit-first.json), [write-15](../golden/api/write-15-double-submit-second.json) |
| 18 | Nightly export file | Windows-1252, CRLF, en-US formats (`3/2/2026 9:15:03 AM`, `150.1500`) | .NET on Linux defaults to UTF-8, LF, invariant or Linux culture | Decision for Phase 7.4: reproduce byte for byte (code page 1252 via `CodePagesEncodingProvider`) or change format with the consumer | [export golden files](../golden/export) |

Each difference that is kept (3, 15, 17, and any decided in Phase 6) is listed in `docs/measurements.md` under
"behaviour differences caught" when the parity tests run.
